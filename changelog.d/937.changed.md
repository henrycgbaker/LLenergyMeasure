Study-wide settings now resolve through one precedence chain, and the run records which layer supplied each value. The results directory, the execution block (cycles, ordering, thermal gaps) and the per-engine runner and image pins all resolve in a single merge - call-site override (a `-o` flag, an API argument) > env var > study file > user config > built-in default - before the study is dispatched. Resolved values are unchanged; what changes is that there is now exactly one answer per setting:

- **The preview and the run always agree.** The preflight panel, `--dry-run` and the runtime previously each re-derived the results directory with their own fall-through (with two different fallback literals); all three now read the same resolved value.
- **Provenance is recorded by the merge itself.** The resolved study carries a `settings_provenance` map naming the layer that won each setting (`call_site` / `env` / `yaml` / `user_config` / `default`), and the per-experiment `config.json` `provenance` section is built from labels the merges emitted rather than inferred afterwards by diffing against defaults. One label from that section is renamed: fields set by a caller override now read `"source": "call_site"` where they previously read `"cli_flag"`.
- **Env pins keep working, at the documented precedence.** `LLEM_RUNNER_<ENGINE>` and `LLEM_IMAGE_<ENGINE>` are read by the chain's env layer. A duplicate internal mechanism that also fed them into the user-config layer (below the study file, so a study could silently outrank your env var in some paths) is gone.

`load_study(path, cli_overrides=...)` is the documented call-site layer: values passed there win over the study file and are labelled `call_site` in the recorded provenance. `run_study(path, cli_overrides=...)` forwards them; for a `StudyConfig` object input the argument is ignored, since the caller already built the config.
