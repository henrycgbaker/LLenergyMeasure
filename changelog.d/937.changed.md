Study-wide settings now resolve through one precedence chain, and the run records which layer supplied each value. The results directory, the execution block (cycles, ordering, thermal gaps) and the per-engine runner and image pins all resolve in a single merge - call-site override (a `-o` flag, an API argument) > env var > study file > caller execution defaults > user config > built-in default - before the study is dispatched. Resolved values are unchanged with one disclosed corner (below); what changes is that there is now exactly one answer per setting:

- **The preview and the run always agree.** The preflight panel, `--dry-run` and the runtime previously each re-derived the results directory with their own fall-through (with two different fallback literals); all three now read the same resolved value.
- **Provenance is recorded by the merge itself.** The resolved study carries a `settings_provenance` map naming the layer that won each setting (`call_site` / `call_site_default` / `env` / `yaml` / `user_config` / `default`), and the per-experiment `config.json` `provenance` section is built from labels the merges emitted rather than inferred afterwards by diffing against defaults. Two consequences for the sidecar's content: fields set by a caller override now read `"source": "call_site"` where they previously read `"cli_flag"`, and a sweep axis declared with a single value is labelled `sweep` where the old inference (which could only see variation) reported `yaml`. A call-site override or swept axis whose value happens to equal the built-in default now keeps its provenance entry instead of being trimmed as "default-equal".
- **Env pins keep working, at the documented precedence.** `LLEM_RUNNER_<ENGINE>` and `LLEM_IMAGE_<ENGINE>` are read by the chain's env layer. A duplicate internal mechanism that also fed them into the user-config layer (below the study file, so a study could silently outrank your env var in some paths) is gone. `make docker-images` now shows the image pin a run would actually use, env and user-config pins included.
- **The user config only speaks when its file does.** Provenance labels a value `user_config` only when your config file actually wrote it; the machine defaults (`./results`, the 60s/300s thermal gaps) are labelled `default` when nothing set them. Resolved values do not move. One deliberate corner does change: a study file declaring an explicit `null` thermal gap ("use the machine default") now falls through to the caller's execution defaults (e.g. the CLI's research protocol) before the user config, matching the documented layer order; previously it skipped past them to the user config.

**BREAK: `run_study(path, cli_overrides=...)` now really applies the overrides.** Previously the argument only annotated provenance; the values never touched the study. Now they are the call-site layer of the load: they deep-merge onto the parsed study file and win over what it declares. Three consequences if you were passing this argument:

- Overrides must be study-file-shaped and nested, e.g. `{"task": {"model": "gpt2"}}` or `{"study_execution": {"n_cycles": 5}}`. The flat and dotted shapes the old docstring showed (`{"model": "gpt2"}`, `{"task.model": "gpt2"}`, `{"dataset.n_prompts": 100}`) are not study-file keys: they now fail loudly at load (`extra_forbidden` / all-configs-invalid) instead of being silently recorded-but-ignored.
- `{"study_execution": {"n_cycles": N}}` now multiplies the dispatched experiment list like any resolved cycle count - the run gets N cycles, not an annotation.
- For a `StudyConfig` object input the argument is ignored (the caller already built the config) - except an already-resolved study (from `api.load_study`), where any override other than the results dir raises `ConfigError` instead of being dropped. `output_dir` applies to already-resolved studies too.

Also in this change, smaller breaks and message changes:

- `api.run_study_preflight` (public API) loses four parameters: `yaml_runners`, `user_config`, `yaml_images` and `user_config_images`. Preflight reads the resolved runner and image pins off the study itself; there is nothing to pass.
- User-config validation errors render field paths dotted (`output.results_dir: ...`) instead of as a Python tuple (`('output', 'results_dir'): ...`) - this applies to every user-config error, not only removed fields.
- Invalid `execution_defaults`/`overrides` values passed to `load_study` are reported as `Invalid execution settings: <field> (from execution_defaults): ...`, naming the argument that supplied the bad value.

`load_study(path, cli_overrides=...)` is the documented call-site layer: values passed there win over the study file and are labelled `call_site` in the recorded provenance. `run_study(path, cli_overrides=...)` forwards them.
