A `serving` module now owns the online-serving mechanics that every OpenAI-compatible engine shares: server placement, launch (a detached sibling container or a host subprocess), the readiness wait, leak-free shutdown, and the streaming HTTP transport. These previously sat one level below the engines that compose them, mixed in with the container plumbing, and the HTTP transport sat inside the load issuer one level above the server itself. Behaviour is unchanged - the emitted `docker run` argv, the readiness semantics, the streaming token counting and the shutdown escalation are all identical - but import paths move for library users. `ProbeRequest`, `ServerPlacement`, `ServerHandle` and the `Server*Error` types move from `llenergymeasure.infra.server_lifecycle` to `llenergymeasure.serving.types`. The launch, readiness and shutdown functions (`launch_container_server`, `launch_process_server`, `await_ready`, `shutdown`, `allocate_free_port`, `server_container_name`, `default_server_log_path`, `DEFAULT_HEALTH_PATH`) move from `llenergymeasure.infra.server_lifecycle` to `llenergymeasure.serving.lifecycle`. `build_server_container_argv`, also previously exported from `llenergymeasure.infra.server_lifecycle`, moves to `llenergymeasure.infra.docker.command`, joining the offline dispatch builder so that every `docker run` argv is built in one place. `HttpxTransport`, `RequestShape`, `CompletionResult` and `require_httpx` move from `llenergymeasure.harness.traffic` to `llenergymeasure.serving.transport`. Each name is imported from the module named above; `llenergymeasure.serving` itself deliberately re-exports nothing, so importing the value and error types does not pull in the launch machinery behind them. `llenergymeasure.harness.Transport` is unchanged, but `HttpxTransport` is no longer re-exported from the `llenergymeasure.harness` facade. There is no compatibility shim: `llenergymeasure.infra.server_lifecycle` is gone.
